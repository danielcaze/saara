# Saara V1.1 — Home screen redesign, settings, drag & drop, English UI

## Context

V1 shipped and passed full review (20-task plan, all reviewed, critical copyEngine race fixed and stress-tested, `fallow` code-smell analysis integrated — see `docs/superpowers/plans/2026-08-11-saara-photo-sorter-v1.md`). Manual SD-card E2E test (`tests/manual/e2e-sd-card-import.md`) is still pending on the user's side.

Using the app for the first time surfaced real UX friction, decided via brainstorming on 2026-08-12:

- The threshold-hours input's native number spinner arrows look bad and clutter the primary flow.
- The two-step Setup → Review flow (pick folders, click "Analisar", wait, see results on a second screen) is slower than it needs to be — picking a source folder should immediately start showing results.
- No drag-and-drop for folders, despite this being a desktop file-management app.
- User is now considering making Saara open source, which changes the calculus on UI language (English reaches more potential contributors/users than Portuguese) and hints at wanting room for project-level info (About/contact) later.

## Decisions (via brainstorming, 2026-08-12)

- **Screens restructure**: `SetupScreen.tsx` + `ReviewScreen.tsx` merge into one `HomeScreen.tsx`. A new `SettingsScreen.tsx` is added. `App.tsx` toggles between `'home'` and `'settings'` via a gear icon on Home; Settings has a back action.
- **Two dropzone boxes, own visual design**: source (left) and destination (right) folder pickers, both click-to-browse (native dialog, as today) *and* drag-and-drop (drop a folder from the OS file explorer directly onto the box). The user showed a reference screenshot of another app's dropzone-with-hint-text pattern — **explicitly not to be copied visually or as a design** (avoiding any plagiarism concern) — only the general UX pattern (dashed dropzone, icon, hint text, bottom status bar with count + action) is reused as a generic, non-proprietary interaction idiom. The actual visual treatment must use Saara's existing dark contact-sheet tokens (`theme.css`): near-black background, `--color-border` dashed outline, `--color-accent` (dark red) highlight on drag-over, Phosphor icons, existing spacing/radius scale — not the reference's macOS chrome, palette, or proportions.
- **Auto-analyze on source pick**: selecting/dropping a source folder immediately triggers analysis (no manual "Analisar"/"Analyze" button) using the currently configured threshold. The group list (reusing `GroupCard` exactly as-is) appears below, scrollable.
- **Sticky bottom action bar**: replaces the current "button after the list" pattern. Shows live file/group count on the left, "Confirm & Copy" button on the right, fixed to the viewport bottom so it's reachable without scrolling through a long list. Disabled until both a source has been analyzed (groups exist) and a destination is picked. Clicking it is the explicit copy-confirmation step (destination selection alone never starts copying — file-safety decision, unchanged from V1's philosophy).
- **Settings screen (new)**: holds the threshold-hours control (moved out of Home), rendered as a plain numeric field with the native spinner arrows removed via CSS (`appearance: none` / `-moz-appearance: textfield`) — same numeric input semantics, just no visible up/down arrows. Room is left structurally (not built) for future settings (Google Drive connection, About/contact info for the open-source project) — no placeholder UI for these yet, just the screen existing as the right home for them later.
  - **Date-format setting was proposed and explicitly dropped**: `DD/MM/YYYY` can't be used verbatim in a folder name on Windows (`/` is an illegal path character), and the user decided `YYYY-MM-DD`-first is the better convention regardless — not worth the complexity of a display-only override. No date-format setting in V1.1.
- **Threshold persists across app restarts**: saved to `app.getPath('userData')/settings.json` (plain JSON, zod-validated on read, no new dependency — consistent with the project's existing zod-everywhere validation convention). Two new IPC channels: `settings:get` (Home/Settings read current value on mount, falling back to the existing 24h default if the file doesn't exist yet) and `settings:set` (Settings writes on change).
- **Drag-and-drop error handling**: dropping a file (not a folder) onto either box must not crash or hang silently — this is a new failure mode V1 never had to handle (V1's native dialog only ever returns real directories). Main-process folder analysis must distinguish "not a directory" from other errors and surface a clear, English, inline message rather than an unhandled rejection.
- **UI language: English, app-wide.** Reverses the earlier V1 decision (Portuguese). This touches: all screen/component text (Home, Settings), zod validation messages (`src/shared/schemas.ts`), the "no date" group label (currently `'Sem data'` in `suggestGroupName.ts` — becomes `'No date'`, including its existing unit test), analyze-phase labels (`scanning`/`reading-metadata`/`clustering` display strings), native folder-picker dialog titles (`src/main/ipc/handlers.ts`), and the two docs that recorded the Portuguese decision (`docs/superpowers/specs/2026-08-11-photo-sorter-design.md`'s UI section note, and `AGENTS.md`'s "Preferred style" line). Assumed rationale: open-source reach — recorded here, not re-asked.
- **Out of scope for V1.1, recorded for V1.2**: a full-screen image viewer/lightbox — click a thumbnail to view it large, navigate one-by-one across *all* photos independent of group boundaries (crossing into the next group when the current one is exhausted), multi-select photos, and remove individual photos from a group before confirming the copy (opt-out per file). Not designed or built now; flagged the same way V1's spec flagged AI-naming and Drive-destination as future work.

## Screens & data flow (V1.1)

```
App.tsx
 ├─ stage: 'home' | 'settings' (gear icon on Home → settings; back on Settings → home)
 │
 ├─ HomeScreen.tsx  (merges old SetupScreen + ReviewScreen)
 │   ├─ SourceDropzone / DestinationDropzone (click-or-drag, side by side)
 │   ├─ on source set → auto-call analyze() with persisted threshold
 │   ├─ GroupCard list (unchanged component) — scrollable
 │   ├─ sticky footer: file/group count + "Confirm & Copy" (enabled once groups exist AND destination set)
 │   └─ post-confirm: same inline copying → done sub-view swap as today (unchanged behavior)
 │
 └─ SettingsScreen.tsx
     ├─ threshold-hours field (no spinner)
     └─ save → settings:set IPC; Home reads settings:get on mount
```

**New IPC channels** (added to `src/shared/ipcChannels.ts`, validated via `src/shared/ipcSchemas.ts`, handled in `src/main/ipc/handlers.ts`):
- `settings:get` → `{ thresholdHours: number }` (reads `userData/settings.json`, returns `{ thresholdHours: 24 }` default if missing/invalid)
- `settings:set` → `{ thresholdHours: number }` in, `void` out (zod-validates, writes `userData/settings.json`)

**Existing `import:analyze` behavior change**: must now gracefully handle a non-directory `sourcePath` (from a bad drop) — `scanFiles`/`analyzeSource` catches the "not a directory" case specifically and the IPC layer returns an error the renderer can display, instead of the current implicit assumption that `sourcePath` is always a valid directory (true today only because it always came from the native dialog).

## Testing

- `settings.json` read/write: unit-testable in `src/main/` the same way other fs-touching modules are (real temp dir, not mocked) — a small `settingsStore.ts`-style module with `getSettings()`/`setSettings()`, TDD like the rest of the main-process code.
- `suggestGroupName.test.ts`: update the existing `'Sem data'` assertion to `'No date'`.
- Drag-and-drop and the visual dropzone/sticky-footer layout are renderer/UI concerns without existing automated coverage precedent in this project (same as GroupCard/Thumbnail today) — verified manually, consistent with how V1's UI tasks were verified.
- Non-directory drop handling: unit-testable at the `scanFiles`/`analyzeSource` level (pass a file path instead of a directory, assert a clear error rather than a thrown/unhandled rejection).
